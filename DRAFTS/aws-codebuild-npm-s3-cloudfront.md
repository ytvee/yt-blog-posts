## Где собирается приложение и где оно работает

Наш buildspec заканчивается двумя операциями: синхронизацией билда с S3 и созданием CloudFront invalidation. Именно они показывают, что результатом деплоя служат статические файлы.

Слово «статические» здесь относится к способу доставки. S3 возвращает сохранённый JS-файл, не вычисляя его заново для каждого запроса. Сам интерфейс при этом может быть сложным: чаты, платежи, редакторы, запросы к API. Их JavaScript выполняется в браузере.

```text
                     СБОРКА В AWS

GitHub ──────────────── исходники ───────────────┐
S3 с конфигурацией ──── .env ────────────────────┤
npm registry ────────── обычные npm-пакеты ──────┤
GitHub Packages ─────── пакет дизайн-системы ────┤
                                               ▼
                                      контейнер CodeBuild
                                      Node.js + npm
                                      TypeScript + Vite
                                               │
                                               ▼
                                             dist/
                                               │
                                               ▼
                                      S3 с файлами сайта

                    ДОСТАВКА ПОЛЬЗОВАТЕЛЮ

Браузер ── запрос HTML / JS / CSS ──► CloudFront ──► S3
   │
   └──── выполнение JavaScript и запросы к API
```

У первой части есть начало и конец. CodeBuild получает исходники, исполняет команды и завершает build. Вторая часть продолжает работать после завершения сборки: S3 хранит результат, CloudFront обслуживает запросы.

Поэтому остановка build-контейнера не выключает сайт. Его файлы уже находятся в другом сервисе.

В репозитории есть `Dockerfile`, но показанный AWS buildspec его не вызывает. В командах нет `docker build`, `docker push` или запуска сервиса ECS. Само наличие Dockerfile рядом с `package.json` не заставляет CodeBuild автоматически собирать образ приложения.

Это утверждение относится к изученному пути деплоя. Как устроен backend, какие ещё сервисы работают в аккаунте и есть ли отдельные контейнерные сборки, из этих логов установить нельзя.

Документация AWS описывает этот раздел ответственности через build project: в нём задаются источник, окружение и команды, которые превращают входные файлы в результат сборки. [Как работает CodeBuild](https://docs.aws.amazon.com/codebuild/latest/userguide/concepts.html).

## Из какого образа запускается CodeBuild

Образ содержит исходную файловую систему среды: операционную систему, программы и библиотеки. Контейнер — запущенная среда на основе этого образа, в которой работают процессы сборки. У работающего контейнера появляются свои изменения файлов: скачанные исходники, `node_modules`, созданный `dist`.

В этом AWS-процессе build image выбирается в настройках CodeBuild project. Он может быть предоставлен AWS или подготовлен командой. Точного имени и тега образа в переданных фрагментах нет. Строка `Running on CodeBuild On-demand` обозначает режим работы сервиса, но не сообщает версию Ubuntu, Amazon Linux или image tag. [Build environment reference](https://docs.aws.amazon.com/codebuild/latest/userguide/build-env-ref.html).

Зато из дальнейших команд видно, что среда умеет выполнять shell-команды, в ней доступны AWS CLI и утилита `n`. Уже внутри этой среды запускается:

```bash
n ${NODE_FROM_FILE:-24}
```

Здесь устанавливается Node.js. Docker-образ не пересобирается. Изменяется файловая система текущей build-среды: `n` скачивает дистрибутив и переключает используемую версию Node. В логе видно скачивание архива `node-v24.14.0-linux-x64.tar.xz`, а затем:

```text
installed : v24.14.0 (with npm 11.9.0)
```

Версию Node выбирает содержимое `.env`, а не строка `FROM` из репозиторного Dockerfile. Поведение менеджера версий описано в [документации n](https://github.com/tj/n).

Последовательность запуска получается такой:

1. AWS подготавливает вычислительные ресурсы и build-среду из выбранного образа.
2. CodeBuild скачивает исходники и получает buildspec.
3. Агент CodeBuild исполняет команды buildspec в этой среде.
4. Команда `n` устанавливает выбранный Node.js.
5. npm устанавливает проектные пакеты.
6. Процессы TypeScript, Vite и Node-скрипта создают результат.
7. AWS CLI отправляет результат в S3 и обращается к CloudFront API.
8. Build завершается. Сохранение данных для следующего запуска требует отдельно настроенных механизмов, например кеша или артефактов.

Первые служебные фазы в полном запуске могут происходить ещё до первой строки предоставленного лога. Поэтому его начало нельзя использовать как точный момент старта контейнера или начала тарификации.

## Как прочитать buildspec

Ниже существенная часть исходного buildspec. Комментарии о неисполняемых командах убраны, действующие команды сохранены. Строки `cat .env` здесь нужны для разбора существующей конфигурации; далее объясню, почему я бы их удалил.

```yaml
version: 0.2

phases:
  install:
    commands:
      - aws s3 sync s3://${CONFIG_BUCKET}/asi-create-ai-foundry .
      - cat .env
      - NODE_FROM_FILE=$(grep -E '^NODE_VERSION=' .env | cut -d '=' -f2)
      - echo $NODE_FROM_FILE
      - n ${NODE_FROM_FILE:-24}

  build:
    commands:
      - node -v
      - echo "//npm.pkg.github.com/:_authToken=\${GH_TOKEN}" > .npmrc
      - echo "@asi-alliance:registry=https://npm.pkg.github.com" >> .npmrc
      - echo "always-auth=true" >> .npmrc
      - cat .env
      - npm install --verbose
      - npm run build
      - cd dist
      - aws s3 sync . s3://"$BUCKET_NAME"/ --delete
      - aws cloudfront create-invalidation --distribution-id "$CLOUDFRONT_DISTRIBUTION_ID" --paths "/*"
```

`version: 0.2` — версия формата buildspec. Она не имеет отношения ни к версии приложения, ни к Node.

Внутри `commands` команды выполняются последовательно. Это даёт нам причинную цепочку: сначала доступ к реестру, затем установка, затем сборка, затем загрузка. Версия buildspec 0.2 также сохраняет shell-состояние между командами, необходимое для присваивания `NODE_FROM_FILE` и последующего `cd dist`. [Справочник buildspec](https://docs.aws.amazon.com/codebuild/latest/userguide/build-spec-ref.html).

### Почему npm install находится в фазе build

Название фазы не запускает пакетный менеджер само по себе. `install` — место, куда автор buildspec записывает команды подготовки. В нашем файле там скачивается `.env` и выбирается Node. npm устанавливает зависимости позже, внутри `build`, потому что именно там записана соответствующая команда.

Аналогично фаза `build` не обязана только компилировать код. В рассматриваемом файле она ещё публикует сайт. Поэтому фраза «сборка упала на BUILD» недостаточна для диагностики: сломаться могли npm, TypeScript, загрузка в S3 или CloudFront API.

Лог показывает `PRE_BUILD` и `POST_BUILD`, хотя пользовательских команд в этих блоках нет. Это этапы жизненного цикла CodeBuild; их присутствие не означает скрытую установку пакетов или дополнительный деплой.

### Что означают две команды s3 sync

Первый вызов читает конфигурацию:

```bash
aws s3 sync s3://${CONFIG_BUCKET}/asi-create-ai-foundry .
```

Источник — S3 prefix, назначение — текущая директория исходников внутри CodeBuild. В рассмотренном логе скачан один `.env`. Сама команда шире: если в этом prefix появятся другие файлы, они тоже могут быть скачаны.

Второй вызов идёт в обратную сторону. После `cd dist` текущая директория содержит готовый сайт, и её содержимое отправляется в deployment bucket.

Config bucket и deployment bucket выполняют разные задачи. Один поставляет вход сборке, другой хранит её результат.

### Откуда взялся buildspec

В логе указан путь `/codebuild/readonly/buildspec.yml`. В изученном checkout файла buildspec нет. Это согласуется с тем, что команды переданы через настройки AWS, но сам путь не доказывает конкретный способ хранения: возможны настройки project и overrides запуска. Для точного ответа нужен раздел Buildspec в CodeBuild и параметры конкретного build.

Не следует дорисовывать и CodePipeline. Его участие подтверждается настройками запуска, а не наличием слова CodeBuild. CodePipeline управляет этапами release-процесса; CodeBuild исполняет работу сборки. [Понятия CodePipeline](https://docs.aws.amazon.com/codepipeline/latest/userguide/concepts.html).

## Почему npm устанавливает сотни пакетов

В изученном `package.json` 44 записи в `dependencies` и 25 в `devDependencies`. Итого 69 прямых зависимостей. В логе npm их уже 673.

Прямая зависимость — пакет, который проект объявляет сам. Транзитивная — пакет, необходимый одной из его зависимостей. Например, текущий lockfile показывает у `@asi-alliance/design-system` зависимости `classnames` и `framer-motion`. У тех есть собственные требования.

```text
Приложение
├── @asi-alliance/design-system
│   ├── classnames
│   └── framer-motion
│       └── другие пакеты
└── vite
    ├── rollup
    ├── esbuild
    └── другие пакеты
```

Это сокращённый пример связей из дерева, а не полная раскладка `node_modules`. npm старается совместно использовать совместимые версии; при несовместимых требованиях в дереве могут существовать несколько версий одного пакета.

Из этого следует практическое наблюдение. Если в логах появился незнакомый пакет, это ещё не означает, что кто-то добавил его прямо в приложение. Он мог прийти через дизайн-систему, линтер или сборщик. Для такого расследования полезна команда `npm explain <package>` внутри диагностической CodeBuild-сборки.

### Три файла и каталога, которые легко перепутать

| Объект | Что он описывает | Как используется в CodeBuild |
|---|---|---|
| `package.json` | Прямые требования проекта и scripts | npm узнаёт, что проект просит установить и что запускать |
| `package-lock.json` | Зафиксированное дерево разрешённых версий и метаданные | npm восстанавливает согласованные версии |
| `node_modules` | Фактически установленные файлы пакетов | Node и инструменты сборки читают эти файлы |
| `dist` | Подготовленный результат сборки | AWS CLI загружает его в S3 |

Lockfile в этом проекте имеет `lockfileVersion: 3`. В нём 722 записи пакетов, но число записей не обязано совпадать с количеством установленных файловых пакетов в конкретной среде. В дереве встречаются optional-пакеты для разных платформ. Кроме того, SHA исходников AWS-сборки не предоставлен: текущий checkout и её lockfile нельзя объявить побайтово одинаковыми.

Поэтому правильное чтение чисел здесь такое: «69 прямых требований в исследованном manifest; 722 записи в исследованном lockfile; 673 добавленных пакета в логе конкретного запуска». Приписывать всю разницу только платформенным пакетам данных недостаточно. [Формат package-lock.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/).

### Как читать версии

Для обычных стабильных версий старше `1.0.0` эти записи задают разные требования:

```json
{
  "vite": "^6.0.6",
  "typescript": "~5.6.2",
  "prettier": "3.8.4"
}
```

`^6.0.6` допускает совместимые версии шестой основной версии; `~5.6.2` ограничивает обновления веткой `5.6`; запись без оператора фиксирует ровно `3.8.4`. Для `0.x` и prerelease-версий правила имеют нюансы, поэтому механически переносить эти примеры на них не стоит. Форматы требований перечислены в [справочнике package.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/).

В нашем lockfile Vite зафиксирован как `6.4.3`. Поэтому строка `^6.0.6` в manifest и запуск `vite v6.4.3` в логе согласуются друг с другом. `package.json` задаёт допустимый диапазон, lockfile уточняет выбранную версию.

## Зачем AWS нужны devDependencies

Слово `dev` сбивает с толку, если понимать его как «используется только на компьютере разработчика». Подготовка production-фронтенда тоже требует инструментов разработки.

В нашем проекте TypeScript и Vite объявлены в `devDependencies`, а `npm run build` вызывает `tsc -b && vite build`. Следовательно, build-среде нужны оба инструмента. После окончания сборки S3 получает созданные ими файлы, поэтому самим инструментам не обязательно попадать в опубликованный сайт.

Это похоже на печать книги. Редактор и печатный станок нужны, чтобы выпустить тираж; читатель получает готовые страницы. В техническом выражении здесь две разные потребности: чем создать JS-файлы и какой код браузер будет исполнять из этих файлов.

| Пакет или группа | Роль в рассматриваемом проекте | Что происходит при деплое |
|---|---|---|
| React, React DOM, Redux | Код интерфейса и состояния | Используемый код включается в bundle |
| Дизайн-система | Компоненты, стили и их зависимости | Нужные части участвуют в сборке |
| TypeScript | Проверка типов | Выполняется внутри CodeBuild |
| Vite и React plugin | Подготовка production-файлов | Выполняются внутри CodeBuild |
| Типы `@types/*` | Информация для TypeScript | Не становятся исполняемыми типами в браузере |
| ESLint, Prettier | Проверки и форматирование | Установка не означает автоматический запуск |
| Vitest | Тестовый инструмент и типы | Тесты этим buildspec не запускаются; типы Vitest указаны в tsconfig |
| `dotenv`, `fs-extra` | Используются `replace-env.js` | Нужны для обработки email templates в build-среде |

Последняя строка особенно полезна. Эти пакеты находятся в `dependencies`, но в показанном скрипте работают при сборке. Категория в manifest не служит точной картой содержимого browser bundle. В bundle попадает код по графу импортов и правилам сборщика, а не потому, что он находится в определённой секции JSON.

Если импортировать библиотеку из `devDependencies` в клиентский код, сама метка `dev` не запретит её включение. И наоборот, неиспользуемый пакет из `dependencies` не обязан целиком оказаться в итоговом JavaScript.

### Почему production build не выключает devDependencies задним числом

Наши команды выполняются так:

```text
npm install --verbose
        ↓
npm run build
        ↓
vite ... building for production
```

Строка Vite относится к последующей сборке. Она не меняет уже завершённую установку пакетов.

В npm 11.9.0 по умолчанию `omit` включает `dev`, если переменная окружения процесса `NODE_ENV` равна `production`; иначе список по умолчанию пуст. Параметры CLI и npm config тоже влияют на результат. Это можно проверить в [определениях конфигурации именно npm 11.9.0](https://raw.githubusercontent.com/npm/cli/v11.9.0/workspaces/config/lib/definitions/definitions.js).

В предоставленном buildspec нет `--omit=dev`. Логи скачивания dev-инструментов и успешная сборка подтверждают их наличие. Но полного окружения CodeBuild у нас нет, поэтому утверждать, что нигде не задан `NODE_ENV`, нельзя.

Отдельный `.env` в директории не равен окружению процесса npm. Обычный `npm install` не загружает этот файл как Vite. К тому, кто и когда читает `.env`, ещё вернёмся.

## Что происходит внутри npm install

Для понимания лога удобно выделить несколько работ: npm читает конфигурацию и manifest, определяет нужное дерево, получает метаданные и архивы, размещает файлы пакетов, запускает разрешённые lifecycle-скрипты и выводит результат. В реальном выполнении сетевые запросы и часть работ перекрываются по времени.

Поэтому verbose-лог не похож на аккуратный учебный список «сначала React, потом TypeScript, затем остальные». Порядок завершения скачиваний зависит от сети, кеша и внутренних задач npm. Нет отдельного обязательного этапа «все dependencies установлены, теперь начинаем devDependencies».

Сопоставим три записи:

```text
npm http fetch GET 200 https://registry.npmjs.org/vitest ... (cache miss)
npm http fetch GET 200 https://registry.npmjs.org/classnames/-/classnames-2.5.1.tgz ... (cache miss)
npm http cache tslib@https://registry.npmjs.org/tslib/-/tslib-2.8.1.tgz ... (cache hit)
```

Это сокращённые примеры из предоставленного вывода; длительности отдельных запросов опущены.

Первый URL указывает на метаданные пакета. Второй — на архив конкретной версии. `200` означает успешный HTTP-ответ. `cache miss` сообщает, что соответствующая операция не была обслужена готовой кешированной записью; `cache hit` относится к попаданию в кеш npm.

Эти строки нельзя складывать как последовательные времена: запросы могут выполняться параллельно. Пять запросов по пять секунд не обязательно занимают 25 секунд общего времени.

### Установка может выполнять код

Пакет может содержать install-time scripts. Некоторые инструменты через них проверяют или готовят бинарный компонент. Поэтому установка зависимостей имеет больше последствий, чем распаковка ZIP-архивов.

Для npm 11.9.0 поведение описано в документации тега этой версии: lifecycle hooks включают `preinstall`, `install`, `postinstall` и другие события. Вывод некоторых скриптов по умолчанию выполняется в фоне; для диагностики предусмотрен `--foreground-scripts`. [Scripts в npm 11.9.0](https://raw.githubusercontent.com/npm/cli/v11.9.0/docs/lib/content/using-npm/scripts.md).

Здесь я специально фиксирую версию. Страница документации «npm 11» со временем обновляется, и правила более позднего minor-релиза нельзя автоматически приписывать старому логу.

Из этого следует разумная граница доступа: токен, доступный build-процессу, стоит ограничивать нужными операциями. Установка непроверенных зависимостей в сборке с широкими правами требует такого же внимания, как запуск любого внешнего кода.

### Почему audit не остановил деплой

После установки npm сообщил:

```text
added 673 packages, and audited 674 packages in 21s
5 moderate severity vulnerabilities
npm verbose exit 0
```

Числа `added` и `audited` относятся к разным счётчикам. Их расхождение на единицу не означает, что «один пакет не смог установиться».

Выход с кодом `0` позволил CodeBuild перейти к следующей команде. Сводка об уязвимостях не стала блокирующей проверкой в этом запуске. Из одной строки `5 moderate` нельзя определить затронутые пакеты, достижимость уязвимого кода и риск для браузера — для этого нужен отчёт audit.

Подсказку `npm audit fix` из лога не стоит превращать в автоматическое исправление во время деплоя. Такое действие может изменить дерево зависимостей непосредственно перед сборкой. Сначала нужно понять изменения и зафиксировать их в исходниках.

<a id="ci"></a>

## Чем npm ci отличается от npm install

Текущая AWS-команда — `npm install --verbose`. Она учитывает lockfile, а не обязательно скачивает «всё самое новое». Если зафиксированные версии удовлетворяют manifest, npm использует их. При несовпадении требований команда может разрешить новые версии и обновить lockfile. [npm install 11.9.0](https://raw.githubusercontent.com/npm/cli/v11.9.0/docs/lib/content/commands/npm-install.md).

Для сборки в CI обычно полезнее более строгий контракт:

```bash
npm ci --include=dev
```

`npm ci` требует lockfile, завершает работу ошибкой при рассинхронизации с manifest, удаляет существующий `node_modules` и не переписывает manifest или lockfile. `--include=dev` явно сохраняет необходимые сборке dev-зависимости. [npm ci 11.9.0](https://raw.githubusercontent.com/npm/cli/v11.9.0/docs/lib/content/commands/npm-ci.md).

Представим учебный пример. В коммит попало изменение версии библиотеки в `package.json`, но соответствующее обновление lockfile забыли. `npm install` может исправить расхождение внутри одноразового контейнера и собрать уже это дерево. `npm ci` остановит сборку и заставит согласовать входные файлы.

Такой отказ полезен: опубликованная версия должна соответствовать проверенным требованиям, а не случайному результату их исправления на build-сервере.

При этом `npm ci` не делает весь деплой неизменяемым. На результат влияют Node, npm, build image, конфигурация `.env`, сетевые источники и scripts. Для полной воспроизводимости фиксировать нужно весь существенный вход. Если lockfile создавался с флагами, меняющими дерево, например `legacy-peer-deps`, параметры CI тоже должны соответствовать этому решению.

В нашем репозитории Dockerfile уже использует `npm ci`. Но AWS buildspec остаётся самостоятельным набором команд. Замена команды в Dockerfile не исправит показанную CodeBuild-сборку.

<a id="registry"></a>

## Как npm получает приватный пакет

У npm в этой сборке два источника. Публичные зависимости скачиваются с `registry.npmjs.org`, а scope `@asi-alliance` настроен на GitHub Packages.

Создаваемый `.npmrc` содержит:

```ini
//npm.pkg.github.com/:_authToken=${GH_TOKEN}
@asi-alliance:registry=https://npm.pkg.github.com
always-auth=true
```

Первая строка привязывает токен к конкретному registry host. Вторая направляет пакеты заданного scope в GitHub Packages. Это отдельная аутентификация: возможность скачать исходники GitHub сама по себе не означает, что npm имеет право скачать пакет. [Работа с npm registry в GitHub Packages](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-npm-registry).

В buildspec перед долларом стоит обратный слеш:

```bash
echo "//npm.pkg.github.com/:_authToken=\${GH_TOKEN}" > .npmrc
```

Он сохраняет буквальный текст `${GH_TOKEN}` в файле. Подстановку выполняет npm при чтении `.npmrc`, используя окружение своего процесса. Это поддерживаемый способ конфигурации. [Справочник .npmrc](https://docs.npmjs.com/cli/v11/configuring-npm/npmrc/).

Теперь полезная проверка понимания. Если в скачанном `.env` лежит строка `GH_TOKEN=...`, увидит ли её npm? Само по себе наличие файла этого не обеспечивает. В показанном buildspec `.env` не экспортируется целиком в shell. Значит, для такого `.npmrc` токен должен приходить в окружение другим способом. Конкретный способ — настройка project, секрет или override — требует проверки в AWS.

Команда `cat .env` только печатает файл. Она не активирует конфигурацию.

В логе npm 11.9.0 есть предупреждение об неизвестном `always-auth`. Это отдельная проблема конфигурации, а не признак отказа авторизации: установка завершилась успешно. При обновлении buildspec эту устаревшую запись стоит удалить и проверить доступ с host-scoped токеном. Подменять предупреждение выводом «токен не работает» оснований нет.

<a id="build"></a>

## Как TypeScript и Vite создают dist

Установка завершилась. Следующая команда — `npm run build`. Для npm слово `build` обозначает script из `package.json`; содержимое этого script определяет проект.

В нашем случае:

```json
{
  "scripts": {
    "build:client": "tsc -b && vite build",
    "email-templates:env-replace": "node replace-env.js",
    "build": "npm run build:client && npm run email-templates:env-replace"
  }
}
```

Операторы `&&` связывают успех этапов. Если TypeScript завершится с ошибкой, Vite не запустится. Если клиентская сборка не закончится успешно, email-скрипт не выполнится. Эти процессы не работают одновременно.

### Откуда берутся команды tsc и vite

npm добавляет исполняемые файлы проектных пакетов в `PATH` для scripts. Поэтому установленный пакет TypeScript предоставляет `tsc`, а Vite предоставляет `vite`. Глобальная установка каждого инструмента не требуется. [Окружение npm scripts](https://raw.githubusercontent.com/npm/cli/v11.9.0/docs/lib/content/using-npm/scripts.md).

### Что делает TypeScript

`tsc -b` обрабатывает проекты, перечисленные в `tsconfig.json`. В исследованной конфигурации включён `noEmit`, поэтому этот шаг проверяет типы без генерации итогового JavaScript приложения. Служебная информация incremental-проверки при этом может записываться отдельно.

Это объясняет, почему TypeScript и Vite стоят рядом: типовая проверка и подготовка browser bundle выполняют разные задачи. Наличие `.ts` и `.tsx` на входе Vite само по себе не заменяет отдельный typecheck.

В `tsconfig.app.json` также указан `vitest/globals`. Это пример того, почему предложение «удалим все тестовые пакеты из build-среды, ведь тесты не запускаются» требует проверки зависимостей конфигурации: их типы уже участвуют в typecheck.

### Что делает Vite

Vite 6 создаёт production bundle на основе входного HTML и графа импортов. Сборка обрабатывает JS/TS/JSX, CSS и ассеты, формирует chunks и ссылки между выходными файлами. В этой версии за production bundling используется Rollup; переносить объяснение из документации другой основной версии Vite следует осторожно. [Сборка в Vite 6](https://v6.vite.dev/guide/build).

В логе нашего запуска:

```text
vite v6.4.3 building for production...
✓ 2249 modules transformed.
✓ built in 15.72s
```

2249 модулей не равны 2249 npm-пакетам. Один пакет содержит несколько модулей, а приложение добавляет собственные исходные файлы.

Среди результатов есть:

```text
dist/assets/index-BH8k1hFC.js  723.66 kB │ gzip: 229.80 kB
```

Хеш в имени помогает разделять версии ресурсов. Размер `gzip` — расчёт сжатого размера в отчёте, а не доказательство, что S3 получил файл `.gz` или что CloudFront уже настроен на выдачу gzip. Способ HTTP-сжатия проверяется отдельно по настройкам CDN и заголовку `Content-Encoding`.

В `vite.config.ts` установлен `chunkSizeWarningLimit: 600`, поэтому chunk размером 723,66 kB вызывает предупреждение. Изменение лимита только меняет порог предупреждения. Чтобы уменьшить передаваемый код, нужно исследовать состав bundle и загрузку функций приложения. [Build options Vite 6](https://v6.vite.dev/config/build-options).

### Зачем обрабатывать email templates после Vite

`replace-env.js` читает `.env` через `dotenv`, находит HTML-файлы внутри `dist/html-templates` и заменяет `%VITE_PUBLIC_PATH%` значением переменной. В логе найдено 17 шаблонов.

Это уже преобразование готового результата. Поэтому нельзя считать деплой законченным сразу после сообщения Vite `built in 15.72s`: после него ещё выполняется часть script `build`.

В manifest есть и другие команды сборки, но AWS вызывает именно `npm run build`. Название `build:prod` не даёт ему специального статуса — npm не выбирает этот script автоматически из-за запуска на AWS.

<a id="env"></a>

## Когда читается .env

В этой цепочке один файл читают разные инструменты в разные моменты.

| Потребитель | Что читает | Для чего |
|---|---|---|
| Shell-команда `grep` | Строку `NODE_VERSION=` | Выбрать Node до установки пакетов |
| Vite | Поддерживаемые env-файлы и окружение | Подставить значения при сборке |
| `replace-env.js` через dotenv | По умолчанию `.env`, либо путь из `DOTENV_CONFIG_PATH` | Подготовить ссылки в email templates |
| npm | Свою конфигурацию и окружение процесса | Registry, token, omit/include и другие настройки |

Vite 6 по умолчанию выполняет `build` в режиме `production`, загружает общие и подходящие mode-specific env-файлы; уже заданное окружение имеет приоритет. Значения, доступные клиентскому коду через `VITE_*`, встраиваются при сборке. [Env Variables and Modes Vite 6](https://v6.vite.dev/guide/env-and-mode).

Учебный пример:

```dotenv
VITE_BASE_URL=https://api.stage.example.com
```

Если приложение использует `import.meta.env.VITE_BASE_URL`, собранный код получает соответствующее значение. Изменение файла в config bucket после публикации само по себе не перепишет уже загруженный JS. Для этого процесса понадобится новая сборка и доставка нового результата.

Название bucket со словом `stage` не переключает Vite в mode `staging`. Среда публикации и режим сборщика — разные настройки. Здесь staging-проект вполне может быть собран production-командой Vite с адресами staging API.

Ещё одна тонкость из исходников: email-скрипт вызывает `dotenv.config` с конкретным путём. Он не обязан повторять весь порядок загрузки mode-specific файлов Vite. Если позднее появится `.env.production`, следует проверить, что frontend и email templates получают согласованные значения.

### Почему нельзя считать VITE_* секретом

Используемые клиентом значения доступны в опубликованном коде. В `VITE_*` допустимы публичные адреса API и другие сведения, которые браузеру разрешено знать. Приватный registry token и серверный секрет таким способом передавать нельзя.

S3-команда отправляет только `dist`, поэтому сам корневой `.env` ей не загружается. Но значение уже могло попасть в JS во время сборки. Проверка «файл .env отсутствует в bucket» не доказывает отсутствие встроенных чувствительных данных.

И отдельно остаются логи. Исходный `cat .env` печатает конфигурацию дважды. Если в ней есть секреты, они оказываются в build output. Для диагностики достаточно выбранных несекретных сведений и проверки наличия переменных. AWS предлагает передавать чувствительные значения через Parameter Store или Secrets Manager. Это не отменяет необходимости контролировать, какие значения код печатает. [Environment variables в CodeBuild](https://docs.aws.amazon.com/codebuild/latest/userguide/create-project.html).

<a id="s3"></a>

## Что именно загружается в S3

После сборки CodeBuild выполняет:

```bash
cd dist
aws s3 sync . s3://"$BUCKET_NAME"/ --delete
```

Точка теперь означает `dist`. Поэтому в deployment bucket отправляются подготовленные HTML, JS, CSS и ассеты. Корневые `node_modules`, исходный `package.json` и `.npmrc` находятся выше и этой командой не копируются.

S3 хранит объекты с ключами. Например, файл `dist/assets/index-BH8k1hFC.js` превращается в объект с ключом `assets/index-BH8k1hFC.js`. «Папки» в интерфейсе S3 помогают ориентироваться, но для запроса нужен полный ключ объекта.

Флаг `--delete` удаляет из назначения файлы, отсутствующие в источнике, с учётом фильтров команды. В нашем вызове фильтров нет. Поэтому такой sync стоит рассматривать как управление всем содержимым указанного назначения, а не как безобидную отправку нескольких новых файлов. [AWS CLI s3 sync](https://docs.aws.amazon.com/cli/latest/reference/s3/sync.html).

В CSV видны операции двух видов:

```text
upload: assets/<new-file>.js to s3://<deployment-bucket>/assets/<new-file>.js
delete: s3://<deployment-bucket>/assets/<old-file>.js
```

Имена здесь обезличены; комбинация upload и delete взята из реального лога.

### Что происходит с открытой вкладкой при удалении старых chunks

Представим страницу, открытую до деплоя. Она уже получила старый `index.html` и основной JS. Пользователь пока не заходил в редактор, поэтому chunk редактора ещё не загружен.

Пока вкладка открыта, новая сборка публикует `editor-NEW.js` и удаляет `editor-OLD.js`. Пользователь нажимает кнопку редактора. Старая версия приложения продолжает ссылаться на `editor-OLD.js`, потому что её код уже находится в памяти браузера. Если старый объект недоступен, динамический импорт завершится ошибкой.

Сброс CloudFront-кеша не переписывает работающую вкладку. Он также не возвращает удалённый объект в S3. В документации Vite 6 описан этот класс ошибок при обновлении и удалении старых assets. [Load Error Handling](https://v6.vite.dev/guide/build#load-error-handling).

Отсюда появляются решения с хранением assets предыдущих релизов, отдельными release-prefixes и управляемой очисткой. Их выбор зависит от требований к откату и длительности пользовательских сессий. Простое добавление invalidation не решает этот вопрос.

### Почему sync не даёт атомарный релиз

Команда обновляет набор объектов по отдельности. Между загрузкой первого и последнего файла существует промежуточное состояние. Даже корректное поведение каждого S3-объекта не превращает весь набор сайта в одну транзакцию.

Практический риск — HTML и JS временно принадлежат разным релизам. Отправка assets перед HTML уменьшает часть риска, но тоже требует продуманной стратегии старых файлов и кешей. Для более строгого переключения используют отдельные наборы файлов релиза и механизм выбора активного набора; в предоставленном buildspec такого механизма нет.

### Кто разрешает запись

AWS CLI должен получить AWS credentials с правами на нужные операции. Для CodeBuild типичный механизм — service role, которую сервис использует для доступа к ресурсам. В её политике разграничивают чтение config bucket, операции в deployment bucket, запись логов и CloudFront invalidation.

`GH_TOKEN` отвечает за GitHub Packages и не заменяет AWS credentials. Если npm скачал дизайн-систему, а `s3 sync` завершился `AccessDenied`, это две разные системы доступа. Точный набор прав нашего проекта из переданных данных неизвестен. [Service roles и настройки CodeBuild](https://docs.aws.amazon.com/codebuild/latest/userguide/create-project.html).

<a id="cloudfront"></a>

## Как CloudFront обновляет сайт

CloudFront принимает запросы пользователей и хранит кешированные ответы. Когда нужного актуального ответа в кеше нет, он обращается к origin. Для рассматриваемой схемы frontend-файлы опубликованы в S3; точную настройку origin нужно подтвердить в distribution.

Статические файлы удобно отдавать через CDN: пользователю не требуется каждый раз обращаться к хранилищу, а часто используемые ресурсы могут обслуживаться из кеша.

После обновления S3 buildspec выполняет:

```bash
aws cloudfront create-invalidation \
  --distribution-id "$CLOUDFRONT_DISTRIBUTION_ID" \
  --paths "/*"
```

Кавычки вокруг `/*` сохраняют wildcard как аргумент CloudFront, чтобы shell не развернул его в имена файлов. Invalidation сообщает CDN, что соответствующие кешированные ресурсы нужно сделать неактуальными. Она не загружает новый `dist`: эта работа уже выполнена предыдущей командой. [Invalidation в CloudFront](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html).

В нашем CSV возвращён статус `InProgress`. После этого фаза BUILD завершилась успешно. Значит, доказано создание запроса, а не окончание обновления всех кешей.

### Пять разных состояний, которые называют «задеплоилось»

| Состояние | Чем его подтвердить |
|---|---|
| Сборка создала `dist` | Успешный `npm run build` и ожидаемые файлы |
| Файлы загружены | Успешный sync и объекты в нужном S3 bucket |
| Invalidation принята | Ответ CloudFront API с ID |
| Invalidation завершена | Статус `Completed` |
| Пользователь получил рабочую версию | HTTP-проверка и проверка функций опубликованного приложения |

Одна зелёная строка не проверяет все пять состояний.

Если процесс должен ждать окончания invalidation, AWS CLI поддерживает waiter:

```bash
aws cloudfront wait invalidation-completed \
  --distribution-id "$CLOUDFRONT_DISTRIBUTION_ID" \
  --id "$INVALIDATION_ID"
```

Это пример возможного дополнения. В исследованной сборке его нет. Ожидание завершения всё равно не заменяет проверку приложения. [CloudFront waiter](https://docs.aws.amazon.com/cli/latest/reference/cloudfront/wait/invalidation-completed.html).

### Здесь несколько кешей

| Кеш | Что ускоряет | Имеет ли отношение к invalidation сайта |
|---|---|---|
| npm cache в build-среде | Повторное получение пакетных данных | Нет |
| Настроенный CodeBuild cache | Повторное использование данных между builds | Нет |
| CloudFront cache | Ответы HTTP пользователям | Да |
| Browser cache | Повторные запросы конкретного браузера | Напрямую не очищается |

Строка npm `cache hit` ничего не говорит о свежести сайта. И наоборот, `/*` в CloudFront не ускоряет установку следующего npm-дерева.

### Почему для HTML и хешированных JS нужны разные решения

У `index.html` имя обычно остаётся прежним, а ссылки внутри меняются. У `index-BH8k1hFC.js` хеш различает версию содержимого. Поэтому распространённая стратегия — регулярно перепроверять HTML и долго кешировать ресурсы с неизменяемыми именами.

Для HTML можно потребовать проверку перед повторным использованием сохранённого ответа:

```http
Cache-Control: no-cache
```

Для действительно неизменяемого хешированного asset можно задать долгий срок хранения:

```http
Cache-Control: public, max-age=31536000, immutable
```

Это пример стратегии, а не обнаруженные настройки проекта. Файлы из `public`, у которых имя не меняется вместе с содержимым, требуют отдельного решения.

Фактическое кеширование зависит и от CloudFront cache policy. Например, положительный minimum TTL может заставить CDN кешировать ответ вопреки части запрещающих заголовков origin. Поэтому проверяют вместе metadata объектов, HTTP-ответы и политику distribution. [Управление сроком кеширования](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Expiration.html).

### Нужно ли делать S3 bucket публичным

CloudFront может читать обычный S3 origin через Origin Access Control, а прямой публичный доступ к bucket можно закрыть. Для website endpoint S3 действуют другие условия: OAC для него не применяется. В показанных логах тип origin не виден, поэтому выбирать архитектуру по одному названию bucket нельзя. [Доступ CloudFront к S3 origin](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html).

### Как сюда вписывается React Router

В исследованном `src/App.tsx` используется `HashRouter`. Адрес вида `https://site.example.com/#/dashboard` передаёт серверу путь перед `#`; фрагмент после него обрабатывается браузером. Поэтому такой внутренний маршрут сам по себе не требует S3-объекта `/dashboard`. [Назначение HashRouter](https://reactrouter.com/api/declarative-routers/HashRouter).

При маршрутизации обычными URL-путями понадобилось бы отдельно согласовать поведение origin при прямом открытии вложенного пути. Но переносить типичный совет «возвращать index.html на любой 404» в наш проект без проверки было бы ошибкой. Более того, если запрос отсутствующего `.js` получит HTML, браузер всё равно не сможет исполнить этот ответ как ожидаемый модуль.

## Что я изменил бы в процессе

Исходный запуск успешно завершил свои команды. Улучшения ниже относятся к предсказуемости, доступам и проверке результата. Они не применены к проекту и не выданы за уже проверенную AWS-конфигурацию.

Начал бы с `cat .env`. Удаление этих строк убирает бессодержательное для сборки действие, которое раскрывает весь файл в логах. Для наблюдаемости оставил бы версии инструментов, SHA исходников и понятные сообщения о начале этапов.

Затем заменил бы установку на `npm ci --include=dev` после проверки согласованности lockfile. Это закрепляет поведение установки и делает наличие build-инструментов явным. Устаревший `always-auth` убрал бы из генерируемого `.npmrc`.

Разделение фаз помогает читать логи, но само по себе ничего не ускоряет. Подготовку Node оставил бы в INSTALL, настройку registry и зависимости перенёс бы в PRE_BUILD, компиляцию — в BUILD, публикацию — в POST_BUILD. При таком переносе обязательно нужен барьер от публикации после проваленной сборки. В примере для этого используется `CODEBUILD_BUILD_SUCCEEDING`: AWS задаёт `1` для успешного на текущий момент build и `0` для проваленного. [Переменные окружения CodeBuild](https://docs.aws.amazon.com/codebuild/latest/userguide/build-env-ref-env-vars.html).

Ниже учебная форма такого изменения. Она предполагает существующий CodeBuild image с `n` и AWS CLI, заданные AWS-переменные, токен в окружении и корректные права. Текущий способ `s3 sync --delete` сохранён для сравнения; его риски для старых вкладок этот пример не устраняет.

```yaml
version: 0.2

phases:
  install:
    commands:
      - aws s3 sync "s3://${CONFIG_BUCKET}/asi-create-ai-foundry" .
      - NODE_FROM_FILE=$(grep -E '^NODE_VERSION=' .env | cut -d '=' -f2)
      - n "${NODE_FROM_FILE:-24}"
      - node --version
      - npm --version

  pre_build:
    commands:
      - |
        test -n "$GH_TOKEN" || { echo "GH_TOKEN is required"; exit 1; }
        printf '%s\n' \
          '//npm.pkg.github.com/:_authToken=${GH_TOKEN}' \
          '@asi-alliance:registry=https://npm.pkg.github.com' > .npmrc
      - npm ci --include=dev

  build:
    commands:
      - npm run build

  post_build:
    commands:
      - |
        if [ "$CODEBUILD_BUILD_SUCCEEDING" != "1" ]; then
          echo "Build failed; deployment is skipped"
          exit 1
        fi
        test -f dist/index.html || { echo "dist/index.html is missing"; exit 1; }
        aws s3 sync dist/ "s3://${BUCKET_NAME}/" --delete
        SYNC_STATUS=$?
        if [ "$SYNC_STATUS" -ne 0 ]; then
          exit "$SYNC_STATUS"
        fi
        INVALIDATION_ID=$(aws cloudfront create-invalidation \
          --distribution-id "$CLOUDFRONT_DISTRIBUTION_ID" \
          --paths '/*' \
          --query 'Invalidation.Id' \
          --output text)
        INVALIDATION_STATUS=$?
        if [ "$INVALIDATION_STATUS" -ne 0 ]; then
          exit "$INVALIDATION_STATUS"
        fi
        aws cloudfront wait invalidation-completed \
          --distribution-id "$CLOUDFRONT_DISTRIBUTION_ID" \
          --id "$INVALIDATION_ID"
```

Пример проверяет код завершения sync до обращения к CloudFront и отдельно проверяет создание invalidation. Если waiter исчерпает ожидание, build может завершиться ошибкой уже после загрузки файлов. Автоматического отката этот YAML не делает.

В текущем manifest нет `prebuild`, поэтому опубликованная цепочка явно не запускает ESLint и тесты. Выделенные проверки перед деплоем стоит добавлять с учётом существующих команд и их готовности работать без интерактивного режима. Пакет, установленный в `node_modules`, сам себе такую проверку не назначит.

### Кешировать стоит измеряемую работу

В предоставленном логе CodeBuild пишет, что cache paths не указаны и кеширование пропущено. При этом npm выводит отдельные `cache hit`. Противоречия нет: npm работает со своим кешем, а сохранение этого кеша между builds — отдельная настройка CodeBuild.

При переходе на `npm ci` часто имеет смысл исследовать кеш npm-архивов: `node_modules` команда всё равно очищает. Для кеширования между запусками нужны согласованные настройки project и buildspec; одной случайной строки в YAML недостаточно. Типы кеша описаны в [CodeBuild caching](https://docs.aws.amazon.com/codebuild/latest/userguide/build-caching.html).

Выигрыш здесь нельзя обещать заранее. В нашем наблюдении установка заняла около 21 секунды, а выбор Node — около 28. Если цель — сократить общее время, нужно измерять оба участка и стоимость восстановления кеша. Образ с уже подходящим Node может убрать часть повторной подготовки, но потребует отдельного управления версиями образа.

### Для отката нужен сохранённый результат

«Снова собрать предыдущий коммит» и «вернуть предыдущий релиз» — разные операции. Старый коммит с новым `.env`, другим npm или изменившимся образом может дать иной результат.

Чтобы вернуть именно предыдущие файлы, их нужно сохранять как определённый release artifact вместе с идентификаторами существенных входов. S3 Versioning помогает хранить версии отдельных объектов, но само по себе не описывает, какой набор HTML, JS и CSS составлял согласованный релиз.

Я бы сначала зафиксировал контракт результата: commit SHA, версии Node/npm, идентификатор сборки, версию конфигурации и сохранённый `dist`. Уже после этого выбирал бы способ переключения релизов и очистки старых assets.

## Как показать всё это на лекции

Эту часть можно использовать как план занятия примерно на 75–90 минут с обсуждением. Первую половину стоит пройти по уже существующим логам. Эксперименты с зависимостями выполняются в отдельном диагностическом CodeBuild project без команд публикации и без прав записи в рабочий deployment bucket.

Примеры ниже подготовлены для демонстрации; результаты дополнительных запусков в AWS в этой статье не заявляются.

### Демонстрация 1. Найти контейнер, в котором всё происходит

Открываем CodeBuild project и раздел Environment. Показываем image identifier, тип compute и service role. Затем открываем конкретный build и его source revision.

Вопрос аудитории: какая из этих настроек отвечает за Node 24.14.0 в предоставленном логе? После ответа показываем команду `n` и строку `NODE_VERSION` из безопасного фрагмента конфигурации. Image создаёт исходную среду, а buildspec затем выбирает runtime внутри неё.

Если образ уже содержит Node, это ещё не означает, что сборка пользуется именно им. Фактическую версию подтверждает `node --version` после настройки.

На этой же странице устанавливаем, кто запускает сборку: webhook, ручной вызов или CodePipeline. До проверки это открытый вопрос, а не часть нарисованной по привычке схемы.

### Демонстрация 2. Проследить один пакет

Берём Vite. В manifest он находится в `devDependencies` с диапазоном версии. В lockfile находим конкретную версию. В CloudWatch находим установку, а затем строку запуска `vite v6.4.3`.

В диагностическую сборку после установки можно добавить:

```bash
npm ls vite typescript @asi-alliance/design-system --depth=0
npm explain vite
npm config get omit
npm config get include
```

Вывод первой команды покажет фактически установленное дерево верхнего уровня, второй — причину присутствия пакета, последующих — только выбранные параметры установки. Полный `env` или содержимое auth-конфига для этой демонстрации не нужны.

Затем задаём вопрос: появится ли `node_modules/vite` в S3? Возвращаемся к `cd dist` и источнику команды sync. Ответ следует из директории публикации, а не из названия категории зависимости.

### Демонстрация 3. Проверить роль devDependencies

Для этого опыта нужен диагностический build с теми же исходниками, runtime и доступом к package registry. Команды загрузки в deployment bucket из него исключены.

Первый вариант:

```bash
npm ci --include=dev
npm run build
```

Второй вариант запускается отдельным build:

```bash
npm ci --omit=dev
npm run build
```

Ожидаемая разница — отсутствие проектных build-инструментов во втором дереве. Точный текст ошибки заранее не подставляем: образ может содержать глобальный `tsc`, а установка может остановиться раньше по другой причине. Для объяснения результата проверяем фактическое `npm ls` и путь к найденной команде.

На лекции полезнее показать причинность, чем добиться заранее написанной ошибки. Если глобальный инструмент случайно замаскировал пропущенную зависимость, это отдельное наблюдение о воспроизводимости среды.

### Демонстрация 4. Увидеть, что установка ещё не строит приложение

Открываем текущий `package.json` и показываем scripts. Для этого проекта корневой install lifecycle не объявляет автоматический вызов build, а buildspec запускает его отдельно.

В логах находим границу между `npm info ok` и `Running command npm run build`. На ней установка уже завершена, а приложение ещё не прошло TypeScript/Vite-сборку.

Дальше показываем `&&` и предлагаем предсказать результат ошибки TypeScript: Vite в этой цепочке не запустится. Так становится понятнее, почему десятки успешных сетевых загрузок npm ничего не говорят об успешности последующей компиляции.

### Демонстрация 5. Проследить файл из лога до браузера

Находим имя JS-файла в выводе Vite. Затем открываем deployment bucket в S3 и находим тот же ключ. Проверяем время изменения и metadata объекта.

После этого открываем опубликованный сайт и Network в браузере. Находим запрос JS, смотрим status, `Content-Type`, `Cache-Control`, `Content-Encoding` и, если присутствуют, `Age` и `X-Cache`.

Это соединяет три наблюдения: что создал Vite, что хранится в S3 и что фактически получил браузер через CloudFront. Одноимённый файл в неправильном bucket здесь обнаружится быстрее, чем по общей надписи `SUCCEEDED`.

Браузер в этой демонстрации открывает AWS-сайт. Никакой сервер на компьютере лектора для опыта не требуется.

### Демонстрация 6. Разделить публикацию и кеш

В CloudFront открываем список invalidations существующего distribution. Находим ID из выбранного build и сравниваем время создания с завершением CodeBuild.

В предоставленном CSV есть `InProgress`, а BUILD уже успешен. Когда в AWS появится `Completed`, сравниваем эти два события. Затем проверяем страницу и запросы ресурсов. Это наглядно показывает, почему статус команды API и проверка пользовательского результата отвечают на разные вопросы.

Для разговора о browser cache можно сравнить обычную перезагрузку и запрос с отключённым кешем в DevTools, проговорив, что этот переключатель относится к браузеру и не очищает CloudFront.

### Демонстрация 7. Обсудить старую вкладку

Рисуем последовательность без запуска разрушительного опыта на рабочем сайте:

```text
Таблица времени        Вкладка пользователя           S3

До деплоя              загрузила основной JS A        assets A
Во время деплоя        продолжает работать             assets B; A удаляются
После деплоя           просит отложенный chunk A       нужного A уже нет
```

Аудитория предлагает, где исправлять проблему: в хранении старых assets, стратегии релизов, обновлении вкладки или обработке ошибки импорта. Затем обсуждаем ограничения каждого решения. Возврат `index.html` вместо отсутствующего JS не восстановит нужный код.

Для первых объяснений достаточно этой схемы и логов delete. Воспроизведение с реальным удалением assets имеет смысл только на отдельном учебном distribution.

### Как распределить время

- 10 минут — схема сервисов и образ CodeBuild.
- 20 минут — package.json, lockfile, npm и devDependencies.
- 15 минут — TypeScript, Vite и конфигурация.
- 15 минут — S3, CloudFront и кеши.
- 15–30 минут — демонстрации, диагностика и вопросы.

Если время ограничено, я бы оставил демонстрации одного пакета и одного файла. Они показывают весь путь без необходимости читать аудитории сотни строк npm-вывода.

## Как искать причину неудачного деплоя

Начинаем с первой команды, которая завершилась неуспешно, и с её контекста. Последнее слово `FAILED` обычно сообщает меньше, чем строка перед ним.

| Симптом | Что проверить первым | Почему |
|---|---|---|
| `401` или `403` при скачивании GitHub package | Scope registry, наличие `GH_TOKEN`, права токена на пакет | Доступ к source repo не равен доступу к package registry |
| `npm ci` отклоняет manifest/lockfile | Соответствие файлов, параметры формирования дерева | CI проверяет вход, а не исправляет его |
| `tsc: not found` или `vite: not found` | omit/include, наличие devDependencies, PATH | Инструмент должен существовать в build-среде |
| Ошибка TypeScript | Файл и диагностику `tsc -b` | Загрузка пакетов уже могла пройти успешно |
| Нет `dist/html-templates` | Предыдущий build и ожидаемую структуру результата | Email-скрипт явно требует этот каталог |
| `AccessDenied` на S3 | AWS identity, IAM/bucket policy, при необходимости KMS | Это права публикации или чтения конфигурации |
| Ошибка CloudFront invalidation | Distribution ID и разрешение API | S3 к этому моменту уже мог быть обновлён |
| CodeBuild успешен, страница старая | Правильный bucket/origin, HTML, cache policy, invalidation, browser cache | Успех shell-команд не проверяет видимую версию |
| Ошибка загрузки JS после деплоя | URL chunk, наличие объекта, тип ответа | Старая вкладка могла запросить удалённый ресурс |
| Сайт открыт, API возвращает ошибку | Встроенный адрес API, ответ backend, auth и CORS | Раздача frontend-файлов и работа backend проверяются отдельно |

Для последнего пункта есть дополнительная ловушка. Настройка proxy в секции `server` файла `vite.config.ts` не превращается в работающий proxy внутри S3 после `vite build`. В опубликованной системе сетевой маршрут API должен обеспечиваться её реальной инфраструктурой и клиентской конфигурацией.

Не стоит исправлять все ошибки одним повторным запуском. Если токен истёк, повтор получит тот же отказ. Если удалён старый chunk, новая сборка не обновит уже открытый код в памяти вкладки. Если рассинхронизирован lockfile, строгий CI будет правильно отклонять его снова.

<a id="questions"></a>

## Вопросы для самопроверки

**Куда исчезает Vite после деплоя?** Он остаётся инструментом завершившейся build-среды. В S3 отправляются созданные файлы из `dist`; постоянный процесс Vite для их раздачи здесь не запускается.

**Почему React нужен в dependencies, если на S3 нет node_modules?** Используемый код React включается в собранное приложение. npm-каталог требуется при подготовке bundle, а браузер получает выходные JS-файлы.

**Можно ли убрать devDependencies, потому что окружение называется production?** Название окружения ничего не говорит о потребностях сборки. В этом проекте без dev-инструментов не обеспечен запуск TypeScript и Vite.

**Почему пакет из dependencies может не попасть в браузер?** Manifest описывает установку. Содержимое клиентского результата определяется импортами, настройками сборки и обработкой неиспользуемого кода.

**Что изменится, если отредактировать .env в config bucket?** Следующая сборка получит новые входные значения. Уже опубликованные файлы от одного редактирования не поменяются.

**Обеспечивает ли package-lock.json полную воспроизводимость сайта?** Он фиксирует дерево пакетов. Версии инструментов, build image, конфигурация и внешние действия scripts остаются дополнительными входами.

**Гарантирует ли invalidation, что старая вкладка начнёт работать на новом коде?** Она изменяет состояние кеша CDN. Уже исполняемый JavaScript в памяти вкладки остаётся прежним до соответствующего обновления приложения.

**Можно ли определить ECS по слову Container в логе?** Нет. Здесь префикс относится к build-среде CodeBuild. Для ECS нужны самостоятельные свидетельства конфигурации и деплоя сервиса.

**Что проверил зелёный BUILD в нашем запуске?** Успешное выполнение настроенных команд, включая принятие invalidation. В нём нет доказательства, что тесты прошли, invalidation завершилась и пользовательский путь работает.

**Где искать точный ответ о том, какой коммит опубликован?** В source revision конкретного build и сохранённых метаданных релиза. Версия `1.1.3` в package.json сама по себе не идентифицирует уникальный commit.
