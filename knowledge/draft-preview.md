# Публичные черновики

## Источник и сборка

Каждый `work/articles/<slug>/current.md` создаёт страницу `_site/drafts/<slug>/index.html`. Название берётся из фронтматтера. Главная `_site/index.html` содержит список по алфавиту, а при отсутствии статей — сообщение «Черновиков пока нет».

После создания или изменения статьи, вставки медиаслотов и публикации выполнить:

```powershell
npm.cmd run build:drafts
```

Сборка заново создаёт только `_site/`. Не создавать HTML вручную. `DRAFTS/`, брифы, история правок и отчёты не публикуются. Наличие файла в `content/` само по себе не скрывает рабочий черновик: он может содержать новую редакцию.

Текст статьи имеет ширину до 600 пикселей, боковые отступы 20 пикселей, системный шрифт 18 пикселей и интервал 1,6. Таблицы и код прокручиваются внутри своих блоков. Поддерживаются обычная разметка Markdown, таблицы, явные якоря `<a id="..."></a>`, разделитель `<div align="center">* * *</div>` и `<video>` с `<source>`. Остальной HTML отображается как текст; служебные комментарии скрыты. Код внутри fenced-блоков сохраняется как код.

Медиа могут использовать HTTP(S) URL либо относительный путь внутри папки этой статьи. Поддерживаемые локальные форматы: PNG, JPEG, GIF, WebP, AVIF, MP4, WebM, OGG, MOV. Сборка копирует только файлы, на которые ссылается текст, включая `poster` видео. Отсутствующее медиа, выход за пределы папки, неподдерживаемый формат или символическая ссылка завершают сборку ошибкой. Ссылки на брифы и ревизии не создают публичных копий этих файлов.

## Деплой и ссылки

GitHub Pages должен использовать источник **GitHub Actions**. Workflow `deploy-drafts.yml` выполняет установку зависимостей, тесты, проверку проекта, сборку и публикацию `_site/` после push в `main` или ручного запуска. Workflow уведомления основного блога работает отдельно.

Получить фактический `page_url` из успешного деплоя окружения `github-pages`. Главная находится по этому URL, статья — по `<page_url>/drafts/<slug>/` (без двойного `/`). До подтверждения деплоя сообщать о локальной готовности, а не о работающей или обновлённой публичной ссылке. Проверять открытие без входа в GitHub и переход из списка к статье.

После успешного `prepare-publication` удаляется только `work/articles/<slug>/`, включая бриф, ревизии и отчёты. Обучение на утверждённой статье должно завершиться заранее. Публичная страница и запись в списке исчезают при следующем успешном деплое; старый URL должен возвращать 404. Сбой сборки или деплоя оставляет предыдущую версию сайта.

На время удаления скрипт сохраняет техническую квитанцию в `work/.publication-cleanup/<slug>.json`. Она позволяет продолжить даже частично выполненное удаление: целевой файл и все оставшиеся рабочие файлы должны совпадать со снимком. При новых правках очистка останавливается. После успеха квитанция удаляется; в публичную сборку она не входит.

Для уже существующих материалов первоначальная очистка разрешена только при полном совпадении SHA-256 `current.md` и соответствующего `content/<slug>.md`. Отличающиеся рабочие версии сохранить. Это техническая проверка хэша, а не чтение `content/` для редакционных задач.

## Пример с двумя статьями

Имена ниже условные; демонстрационные статьи не нужно добавлять на сайт.

1. Агент создаёт `work/articles/first-note/current.md` и `work/articles/second-note/current.md` по обычному редакционному процессу, затем запускает сборку. В списке две ссылки: `drafts/first-note/` и `drafts/second-note/`.
2. Пользователь правит `first-note`. Агент сохраняет ревизии и обновляет `current.md`, затем собирает страницы. URL статьи остаётся прежним; после push и деплоя по нему доступна новая версия. `second-note` остаётся в списке.
3. Пользователь утверждает `second-note`. После медиаплана и обучения агент запускает `node scripts/prepare-publication.mjs --slug second-note --approved-by user`. Скрипт проверяет шлюз, копирует статью в `content/second-note.md`, сверяет хэш и удаляет только `work/articles/second-note/`.
4. Агент запускает сборку. Теперь в списке только `first-note`, а `_site/drafts/second-note/` отсутствует. После push и успешного деплоя агент проверяет тот же результат на публичном сайте и 404 по прежнему URL `second-note`.
5. Повтор команды публикации `second-note` ничего не меняет. Если копирование или проверки не прошли, рабочая папка остаётся. При отдельной ошибке очистки агент сообщает, что файл скопирован, но очистка не завершена, и устраняет причину до повторного запуска.
