Toast уже появился на экране, а счётчик в header всё ещё показывает старое значение. Через несколько секунд badge обновится, уведомление попадёт в modal и на полную страницу. Со стороны это похоже на задержку одного механизма. В нашей реализации это два независимых контура, которые встречаются только на уровне пользовательского опыта.

Мы сознательно разделили доставку. SSE нужен, чтобы сразу показать событие. HTTP inbox нужен, чтобы восстановить историю после перезагрузки, разрыва соединения или пропущенного realtime-сообщения. Такое решение оставляет небольшое окно рассогласования, зато у каждого канала одна понятная работа.

## Два контура одной системы

Главная развилка появляется ещё до выбора Redux, React hooks или библиотеки компонентов. Уведомление одновременно выполняет две разные задачи.

Первая задача — прервать текущий контекст и быстро сообщить о событии. Здесь задержка заметна, а долговременное хранение не нужно. Вторая — остаться в истории, повлиять на счётчик непрочитанных и быть доступной после перезагрузки. Здесь важнее согласованность с сервером.

Мы направили эти задачи по разным веткам:

```text
Notification service
├── SSE /notifications/stream
│   └── EventSource singleton
│       └── NotificationsProvider
│           ├── активное окно → Snackbar queue → Toast
│           └── фоновое окно → hidden buffer → Toast после focus
│
└── HTTP /notifications
    └── runtime parser
        └── последовательный polling
            └── Redux entity cache
                ├── latestIds → badge и modal
                └── page ingestion → страница уведомлений

Пользовательское действие
└── HTTP mutation → local override → selectors → UI
                                  ↑
                  следующий polling подтверждает состояние
                  и удаляет временный override
```

SSE-событие не записывается напрямую в inbox. Оно создаёт toast. Затем ближайший HTTP polling получает серверную запись, нормализует её и добавляет в Redux. Поэтому уже показанный toast может опережать badge и списки на 15 секунд плюс время самого запроса.

У рассогласования есть граница. Если SSE временно недоступен, inbox продолжит работать. Если realtime-событие потерялось, запись придёт по HTTP. Если пользователь не открывал modal, toast всё равно появится. Мы отказались от иллюзии единого канала и получили два независимо восстанавливаемых поведения.

<a id="sse"></a>

## Как живёт SSE-соединение

SSE transport построен вокруг одного `EventSource` на всё приложение. Подписчиков может быть несколько, но физическое соединение одно. Иначе provider, modal или будущий consumer могли бы открыть собственные streams, задублировать события и увеличить нагрузку на notification service.

Singleton рассылает входящее уведомление snapshot-копии подписчиков. Подписчик может отписаться прямо во время callback, не ломая текущий обход. Ошибка одного callback также не останавливает остальные.

После удаления последнего подписчика соединение закрывается не сразу. Мы оставляем grace period 150 мс. Если за это время появляется новый subscriber, отложенное закрытие отменяется, а существующий stream продолжает работу. Это убирает лишние переподключения при быстрых mount и unmount, в том числе в development Strict Mode.

Ручного reconnect в клиенте нет. Пока `EventSource` не закрыт, браузер сам пытается восстановить соединение после transport error. При logout всё меняется: provider очищает данные inbox, SSE-hook удаляет отложенные realtime-события и закрывает stream. Иначе после смены сессии новый пользователь мог бы увидеть остатки уведомлений предыдущего.

С аутентификацией у SSE есть отдельное ограничение. `EventSource` не позволяет произвольно добавить bearer header, как Axios. Cross-origin stream подключается с credentials, а backend должен уметь авторизовать соединение по cookies. Общий Axios interceptor к этой ветке не относится.

Полученное событие показывается сразу только тогда, когда документ видим и окно находится в focus. В фоне notification складывается в память. После возвращения пользователя очередь очищается и каждый накопленный элемент превращается в toast. Это спасает transient-события, но создаёт риск: размер буфера не ограничен, поэтому после долгого отсутствия можно получить целую серию устаревших сообщений.

В Snackbar queue одновременно видны максимум три toast. Остальные ждут своей очереди, причём таймер временного toast стартует только после фактического появления на экране. Из server-driven действий в один toast попадают максимум две.

<a id="http-inbox"></a>

## Как HTTP восстанавливает inbox

HTTP-контур стартует для аутентифицированного пользователя, если вкладка видима и приложение находится вне login, signup или recovery flow. При возврате на вкладку синхронизация начинается сразу. Пользователь не ждёт очередной интервал.

Мы используем последовательный `setTimeout` с интервалом 15 секунд после завершения запроса. `setInterval` мог бы запустить новый sync, пока предыдущий ещё ждёт сеть. В текущей схеме пять секунд ответа сдвигают следующий старт примерно на двадцатую секунду от начала прошлого запроса. Перекрывающихся запросов нет.

Дополнительный флаг защищает от повторного запуска, а `AbortController` останавливает активную загрузку при logout, скрытии вкладки, переходе на auth route или размонтировании provider. Cancellation считается штатным завершением. Обычная сетевая ошибка помечает inbox как устаревший, но не ломает будущие попытки. Успешный sync снимает stale-флаг и сохраняет время обновления.

Между сетью и Redux стоит runtime-парсер. TypeScript описывает ожидания разработчика, но JSON с backend может им не соответствовать. Парсер переводит snake case в camel case, проверяет обязательные поля и нормализует расширяемые значения.

Неизвестный UI type становится информационным, неизвестное действие отбрасывается, а повреждённый элемент не уничтожает весь массив. Для inbox обязателен `createdAt`, потому что он участвует в сортировке. Для realtime-toast допустим timestamp текущего момента: такой toast ещё полезен, даже если stream payload неполон.

Это tolerant reader с понятной границей. Он старается сохранить полезную часть ответа, но не пропускает в доменную модель произвольный объект.

<a id="redux"></a>

## Зачем Redux хранит entities и окна отдельно

После парсинга HTTP-уведомление попадает в нормализованный entity cache. Одна запись хранится один раз и используется в header, modal и на странице. Сортировка newest-first задаётся централизованно.

В статье достаточно увидеть границу данных без reducer-кода:

```ts
interface InboxNotification {
    id: number;
    uiType: 'accept_decline' | 'button' | 'underline_button' | 'info';
    status: 'error' | 'info';
    content: NotificationContent;
    sender: NotificationSender | null;
    context: NotificationContext;
    createdAt: string;
    updatedAt: string | null;
    isRead: boolean;
}

interface StreamNotification extends InboxNotification {
    snackType: 'temp' | 'const';
}

interface NotificationState {
    ids: number[];
    entities: Record<number, InboxNotification>;
    latestIds: number[];
    pendingIds: number[];
    localOverridesById: Record<number, NotificationLocalOverride>;
    latestFeedVersion: number;
    readStateVersion: number;
    pollingError: string | null;
    lastSyncAt: string | null;
    isPollingStale: boolean;
}
```

Самое важное поле рядом с entities — `latestIds`. Оно хранит идентификаторы последнего HTTP-окна из десяти уведомлений. Header и modal работают только с этим окном. Пагинация полной страницы добавляет старые entities в общий кеш, но не меняет `latestIds`.

Без этого разделения кеш отвечал бы сразу на два вопроса: «что мы когда-либо загрузили» и «что сейчас относится к последним уведомлениям». После прокрутки страницы старая запись могла бы внезапно попасть в modal. Отдельное окно не позволяет истории загрязнить актуальный feed.

Selectors получают entity, накладывают локальное изменение, скрывают отменённые приглашения и только потом делят результат на read и unread. Компоненты видят готовую проекцию. Они не знают ни о задержке backend, ни о reconciliation, ни о внутреннем устройстве entity adapter.

У badge есть точная семантика: он считает непрочитанные записи только в окне из десяти последних уведомлений. Значение не поднимется выше десяти, даже если на сервере непрочитанных больше.

Modal использует то же окно, ставит unread раньше read и показывает максимум пять карточек. Страница работает со всеми загруженными entities, но хранит собственную навигацию отдельно.

<a id="overrides"></a>

## Как локальные изменения переживают задержку сервера

После успешного mark-as-read сервер может ещё некоторое время возвращать прежнее `isRead: false`. Если сразу доверять следующему polling, карточка визуально откатится в непрочитанное состояние.

Мы не переписываем server entity вручную. После успешной mutation рядом с ней появляется local override. Selector накладывает его поверх серверных данных, и пользователь видит новое состояние. Когда очередной HTTP-ответ приносит такое же значение, override больше не нужен и удаляется.

Так мы сохраняем происхождение данных. Entity остаётся последним известным ответом сервера, override описывает временную локальную коррекцию, а selector собирает итоговый вид.

Mark-as-read при этом не optimistic: локальное `isRead` меняется после успешного PATCH. Пока запрос выполняется, ID лежит в `pendingIds`, поэтому повторное нажатие блокируется. Accept и decline приглашения используют тот же механизм, но дополнительно обновляют связанные списки collaborations, spaces и invites.

Версии `latestFeedVersion` и `readStateVersion` передают изменения в пагинацию. Первая растёт, когда изменилось актуальное окно. Вторая — после локальной смены read или invitation state. Страница получает семантический сигнал и может пересчитать вкладки с начала, не подписываясь на случайные изменения object identity.

<a id="pagination"></a>

## Почему страница уведомлений сложнее modal

У страницы две вкладки: все уведомления и только непрочитанные. Redux хранит общие entities, а выбранная вкладка, видимые ID и cursor остаются локальным состоянием страницы. Эти данные описывают навигацию конкретного экрана и не нужны header или modal.

Вкладка «Все» должна сначала показать unread, а затем read. Backend фильтрует эти группы отдельно, поэтому одного offset недостаточно. Cursor хранит `unreadOffset`, `readOffset` и признак, что непрочитанные закончились.

Если размер страницы равен десяти, а первый запрос вернул шесть unread, оставшиеся четыре места заполняются отдельным запросом read. Следующая загрузка продолжит read feed с собственного offset. Уникализация ID защищает список от повторов после refresh или сдвига серверной пагинации.

Когда меняется актуальное окно или локальный read state, hook обновляет уже открывавшиеся вкладки с начала и сохраняет текущую глубину списка. Если в этот момент идёт запрос, refresh не стартует параллельно. Он запоминается и выполняется после завершения активной загрузки.

Этот участок хорошо показывает границу состояния. Доменная запись общая, а cursor принадлежит экрану. Перенос cursor в глобальный slice сделал бы Redux владельцем деталей одной страницы и усложнил бы независимую синхронизацию modal.

<a id="presentation"></a>

## Где заканчивается доменная модель

Backend notification не передаётся прямо в компонент карточки. Между ними стоит presentation constructor. Он выбирает fallback avatar, форму изображения, ссылку на profile или сущность, варианты кнопок, resolved status приглашения и максимум две action.

Компонент получает готовую модель и отвечает за отображение и события пользователя. Он не разбирает server URL, не извлекает invitation ID и не знает устройство `context.extraData`. Transport schema и JSX меняются по разным причинам, поэтому мы не связываем их напрямую.

Настройки уведомлений проходят ещё по одной границе. Они нужны единственной странице, поэтому загружаются в локальное React state и обновляются оптимистично с rollback при ошибке. Переносить их в inbox slice только из-за общего слова «уведомления» не понадобилось.

<a id="ограничения"></a>

## Какую цену мы платим

У архитектуры есть конкретные ограничения.

- Toast опережает inbox на интервал polling плюс длительность запроса. SSE не обновляет badge напрямую.
- Badge считает unread только среди десяти последних записей. Его нельзя трактовать как общее число непрочитанных на сервере.
- Буфер фоновых toast не ограничен и не дедуплицируется.
- Проверка равенства entities учитывает не все поля. Изменение только `uiType`, заголовка, timestamp, context ID или списка перемещённых агентов может не вызвать upsert.
- Переход по карточке ждёт успешного mark-as-read. Временная ошибка notification service блокирует навигацию.
- Redux уже хранит `pollingError` и stale-состояние, но интерфейс их не показывает.
- Для provider, stream, reducers, selectors, пагинации и actions нет notification-specific tests. Самые чувствительные места — reconciliation overrides, два offset, lifecycle SSE и побочные эффекты приглашений.

Этот список задаёт карту рисков для следующих изменений. Например, прямое добавление SSE-события в Redux сократит задержку badge, но потребует дедупликации с HTTP, правил сортировки и ответа на вопрос, что делать с неполным stream payload. Локальная правка одного симптома меняет контракт между контурами.

<a id="принципы"></a>

## Что можно перенести в другую систему

Из этой реализации мы бы сохранили несколько границ.

Разделяйте быстрый сигнал и восстанавливаемую историю, если у них разные гарантии доставки. Не заставляйте realtime transport изображать базу данных.

Нормализуйте сетевой payload до записи в общее состояние. Типы TypeScript заканчиваются там, где начинается чужой JSON.

Отделяйте entity cache от окон выдачи. Набор загруженных записей, последние уведомления и видимая страница отвечают на разные вопросы.

Храните временную локальную коррекцию рядом с серверным состоянием, но не выдавайте её за ответ сервера. Тогда reconciliation становится явной частью модели.

Оставляйте navigation state владельцу экрана. Общие entities полезны всему приложению, cursor конкретной вкладки — нет.

И держите перевод доменной модели в UI отдельно от компонентов. Карточка уведомления быстро превращается в место, где смешиваются transport, бизнес-правила, навигация и дизайн-система. Constructor оставляет эти решения на одной проверяемой границе.

Наша система не скрывает разницу между realtime и inbox. Она использует эту разницу: SSE быстро привлекает внимание, HTTP возвращает фактическую историю, а Redux и selectors согласуют оба ожидания на стороне интерфейса.
