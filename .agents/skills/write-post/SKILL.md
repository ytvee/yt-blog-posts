# Написать статью

## Загрузить контекст

Обязательно прочитать:

- `../../../knowledge/author-style.md`;
- `../../../knowledge/headline-policy.md`;
- `../../../knowledge/editorial-policy.md`;
- `../../../knowledge/blog-format.md`;
- `../../../knowledge/source-policy.md`;
- `../../../memory/diversity-profile.md`;
- три последние записи из `../../../memory/article-ledger.md`;
- `../../../templates/article-brief.md`;
- `../../../templates/blog-post.md`.

Читать один или два файла из `../../../examples/articles/` только для дополнительной калибровки стиля. Не читать Telegram-примеры по умолчанию.

Никогда не читать файлы из `../../../content/`: это выход публикационного процесса, а не источник тем, текста, стиля или редакционной памяти.
Для русской вычитки загрузить `../ru-text/SKILL.md` и `../ru-text/references/info-style.md`. `humanizer-ru` применять после написания только в ручном режиме аудита: не запускать Python, не добавлять намеренные ошибки и не заменять нормативное тире дефисом.

## Подготовить материал

1. Выделить из запроса тему, цель, тезис, читателя, факты, личные истории, цитаты, источники и ограничения.
2. Отделить слова автора от внешних фактов и собственных предположений.
3. Не дополнять пробелы вымышленным опытом. Задать один короткий вопрос, только если без ответа нельзя честно построить статью.
4. Выбрать режим:
   - `личное эссе` — если основу составляет прожитый опыт или изменение автора;
   - `экспертно-практический материал` — если основу составляет тезис, метод или разбор с примерами.
5. Использовать уже созданный рабочий `latin-kebab-slug`, содержащий только `a-z`, `0-9` и дефисы.
6. Сформулировать основной вопрос статьи одним предложением.
7. Подготовить 7–10 вариантов заголовка из разных углов по `headline-policy.md`, удалить варианты без достаточных фактов или авторского опыта и выбрать самый конкретный честный вариант.
8. Связать выбранный заголовок и каждый раздел плана с материалами автора или проверенным источником.

## Создать файлы

1. Создать `../../../work/articles/<slug>/revisions/`.
2. Заполнить `../../../work/articles/<slug>/brief.md` по шаблону брифа.
3. Зафиксировать в брифе статусы всех значимых утверждений: `подтверждено`, `со слов автора`, `требует проверки` или `мнение`.
4. Создать `../../../work/articles/<slug>/current.md` по шаблону статьи.
5. Заполнить фронтматтер:
   - использовать текущую дату в формате `YYYY-MM-DD`;
   - оставить `ogImage: ""` и `published: false`;
   - рассчитать `readingTime` командой `node scripts/reading-time.mjs <путь> --write`.
6. После пересчёта `readingTime` сохранить содержимое `current.md` без изменений в `revisions/000-initial.md`.
7. Проверить, что `current.md` и `revisions/000-initial.md` идентичны.
8. Не перезаписывать и не удалять `000-initial.md` при следующих правках.
9. Не добавлять изображения на этом этапе: заглушки создаёт `plan-article-images` перед апрувом.

## Написать и проверить

- Начать с конкретной ситуации, личного повода или тезиса.
- Сохранить данные автором формулировки, факты и характерные детали.
- Не делать текст искусственно симметричным.
- Не добавлять стандартное заключение или призыв к действию без необходимости.
- Выполнить редакторский проход по `editorial-policy.md`.
- Провести ручной аудит по `humanizer-ru`, сохраняя зелёные абзацы, факты и авторскую типографику.
- Проверить черновик командой:

```powershell
node scripts/validate-project.mjs work/articles/<slug>/current.md
```

Исправить ошибки валидации до завершения. В ответе сообщить пути к брифу и статье, а также перечислить только реально оставшиеся вопросы или непроверенные факты.
Выполнить `npm.cmd run build:drafts` по `../../../knowledge/draft-preview.md`. HTML создаётся автоматически из `current.md`. После подтверждённого деплоя сообщить публичную ссылку на черновик; до деплоя сообщить только готовность локальной сборки.
Перед завершением повторно проверить контракт заголовка: каждый его смысловой элемент должен быть раскрыт в текущей версии статьи.
